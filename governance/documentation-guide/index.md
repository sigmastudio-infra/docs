# 사내 위키 문서 작성 가이드

이 문서는 사내 공유 위키에 문서를 작성하고 검수할 때 적용하는 공통 기준을 정의합니다.

## 문서 분류와 디렉터리

- `guide/`: 콘솔 설정과 SDK 연동 같은 절차형 가이드
- `setup/`: 개발 환경 설정
- `design/`: 시스템과 기능 설계
- `governance/`: 저장소, 브랜치와 문서 운영 정책

카테고리에 관계없이 문서 하나당 폴더 하나를 사용합니다.

- 폴더 이름은 영문 kebab-case로 작성합니다.
- 본문 파일 이름은 `index.md`로 통일합니다.
- 이미지는 문서 폴더 아래 `images/`에 저장합니다.
- 이미지 파일 이름은 `<문서 폴더명>-<번호>.png` 형식으로 작성합니다.

## 문장과 용어

- 본문은 한국어로 작성하고, 제품명과 기술 용어는 공식 영문 표기를 사용합니다.
- 영문 UI 문장을 한국어 어순으로 그대로 옮기지 않습니다. 사용자가 해야 할 행동과 확인할 결과가 드러나는 자연스러운 한국어 문장으로 씁니다.
- 버튼, 메뉴, 필드와 옵션 이름은 실제 화면에 표시된 표기를 그대로 사용합니다.
- 메뉴 이동 경로를 한국어로 설명할 때는 바로 아래에 영문 경로를 함께 적습니다.
- 한 문장에는 하나의 핵심 내용만 담습니다.
- 개념과 이유는 완전한 문장으로 설명하고, 절차와 선택지는 목록으로 분리합니다.

### 굵은 글씨

굵은 글씨는 독자가 화면에서 직접 찾아야 하는 UI 이름이나 처음 정의하는 핵심 용어에만 사용합니다.

- 버튼, 메뉴, 필드와 옵션 이름
- 단계 수행에 필요한 핵심 값
- 문서에서 처음 정의하며 이후 계속 사용하는 핵심 용어

문장 전체, 단순한 요약이나 과정 나열에는 굵은 글씨를 사용하지 않습니다. 정보 구조는 굵은 글씨 대신 제목과 목록으로 표현합니다.

### 인라인 코드와 인용

- 명령어, scope, package name, URL 파라미터처럼 독자가 그대로 입력하거나 비교할 값은 인라인 코드(`code`)로 표기합니다.
- 문장 속에서 일반 개념으로 언급하는 제품명과 기술 용어에는 인라인 코드를 사용하지 않습니다.
- 큰따옴표는 공식 문서의 직접 인용과 화면에 실제로 표시되는 상태 메시지에만 사용합니다.

## 문서 도입부

도입부는 다음 순서로 작성합니다.

1. 문서의 목적을 한 문장으로 설명합니다.
2. 문서에서 다루는 주요 과정을 실행 순서대로 나열합니다.
3. 각 과정은 한 줄에 하나씩 적습니다.
4. 필요한 계정, 권한과 사전 설정은 선행 조건으로 분리합니다.

도입부에 문서 작성 방식이나 저자의 작업 메모를 넣지 않습니다. 공통 작성 규칙은 이 문서에서 관리하고, 미완료 작업은 필요한 위치에 TODO로 표시합니다.

## 절차형 가이드

- 한 단계에는 하나의 행동만 작성합니다.
- 화면이 바뀌면 단계를 나눕니다.
- 단계마다 어떤 화면이나 상태가 나타나면 완료인지 설명합니다.
- 사용자가 입력할 값은 값의 출처와 사용 위치를 함께 설명합니다.
- 공식 설정 절차를 재현하는 경우 가능한 범위에서 공식 문서의 장·절과 대응시킵니다.
- 공식 문서 인용은 실제 heading anchor를 확인한 뒤 해당 절의 링크를 사용합니다.
- 화면에 없는 배경 설명이나 팁은 `NOTE`, `TIP` 또는 `QUESTION` 콜아웃으로 절차와 분리합니다.

## 스크린샷

콘솔과 실기기 스크린샷은 실제 작업 화면을 직접 캡처합니다.

- 문서 설명과 현재 UI가 다르면 실제 UI를 기준으로 본문을 갱신합니다.
- 한 스크린샷에는 하나의 지시 또는 확인 목적만 둡니다.
- 독자가 확인해야 하는 영역이 식별 가능해야 합니다.
- 화면을 재생성하거나 UI 내용을 임의로 변경하지 않습니다.
- 계정 이메일, 초대 링크와 프로젝트 식별자는 공유 범위에 따라 마스킹합니다.
- Client Secret, authorization code, access token과 session token은 완전히 가립니다.
- 비밀값이 포함된 이미지는 Git 이력에 추가하기 전에 제거하거나 안전하게 다시 캡처합니다.
- Figma 등 외부 편집 도구에는 비밀값을 가린 사본만 올립니다. 원본 이미지에 비밀값이 있었다면 편집본을 만든 뒤에도 원본의 저장소·공유 이력 노출 여부를 확인합니다.

Obsidian에서는 `![[파일명.png]]` 형식으로 이미지를 삽입합니다. 붙여넣기로 vault 루트에 생성된 이미지는 문서의 `images/` 디렉터리로 옮기고 문서 등장 순서에 맞춰 이름을 정리합니다.

## 비밀정보와 로그

- OAuth Client Secret, authorization code, access token과 session token은 문서, 이미지, 예제 코드, Unity Console 및 Logcat에 표시하지 않습니다.
- Client ID와 프로젝트 ID 같은 식별자가 공개 가능한지 확인하고, Client Secret이나 token과 구분합니다.
- 예제 코드는 credential이나 token을 출력하도록 작성하지 않습니다.
- 검수용 로그가 필요하면 비밀값 대신 성공 여부, 실패 분류와 안전한 correlation ID만 기록합니다.
- 비밀값이 노출된 문서나 이미지는 마스킹만 하고 끝내지 말고 Git 이력과 공유 기록의 노출 여부도 확인합니다.

## 링크와 출처

- 다른 위키 문서는 `[[카테고리/<슬러그>/index|표시 이름]]` 형식으로 연결합니다.
- 같은 문서의 특정 절은 `[[#헤딩|표시 이름]]` 형식으로 연결합니다.
- 외부 링크의 광고 및 추적 query parameter는 제거합니다.
- 공식 문서를 근거로 사용할 때는 해당 내용을 지원하는 절로 직접 연결합니다.
- 원문을 인용하면 인용문과 출처를 함께 표시합니다.

## Obsidian 형식

- frontmatter의 `aliases`에는 한국어 문서 제목을 넣고 H1 제목과 일치시킵니다.
- 질문은 `> [!QUESTION]`, 주의사항은 `> [!WARNING]`, 보충 정보는 `> [!NOTE]` 또는 `> [!TIP]`을 사용합니다.
- 직접 추가해야 하는 스크린샷은 해당 절에 `> [!TODO]` 콜아웃으로 표시합니다.
- 아직 내용이 없는 문서는 본문에 `TODO` 한 줄만 둡니다.

## 검수 기준

- 문서의 단계와 현재 UI 흐름이 일치하는지 확인합니다.
- UI 명칭, package name, Client ID의 출처처럼 혼동하기 쉬운 값을 다시 확인합니다.
- 각 단계에 행동과 완료 조건이 있는지 확인합니다.
- 불필요한 굵은 글씨와 중복 설명을 제거합니다.
- 링크, 이미지 경로와 문서 내 heading 링크가 유효한지 확인합니다.
- 문서, 이미지와 예제 코드에 credential이나 token이 노출되지 않았는지 확인합니다.
